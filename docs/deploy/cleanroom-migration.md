# Переезд cleanroom.uz с Vercel на собственный сервер

Составлено 22.09.2026. Конфиг и проверки лежат рядом:
`deploy/nginx/cleanroom.uz.conf`, `scripts/deploy/gen-nginx.py`,
`scripts/deploy/test-nginx.py`, `scripts/deploy/parity-check.py`.

## ⚠ Целевой сервер = выводимый из эксплуатации (проверено 22.09.2026)

Пользователь указал целевым сервер serverplus.uz, где сейчас работает
prouniforma.uz — это **185.196.219.223** (он же `10.10.4.11` изнутри),
старый 1С-Битрикс. По плану миграции prouniforma именно он выводится из
эксплуатации: prouniforma переезжает на новый хост (`10.100.1.1`, ключ
`~/.ssh/prouniforma-web-key`), а битриксовый после переезда гасится
(`docs/migration/cutover-runbook.md`).

**Развилка для решения пользователя:**
- Ставить cleanroom.uz на битриксовый сервер = переезжать дважды (его
  скоро гасят). Не рекомендуется.
- Логичнее — на новый хост prouniforma (`10.100.1.1`), куда уедет и
  prouniforma. Тогда оба сайта на одной новой машине.

**Доступ по SSH.** 185.196.219.223:22 открыт снаружи, но принимает только
ключ (publickey), пароль из `.env` отклоняется. Подбор ключей/пользователей
я намеренно не делаю. Нужно одно из: (а) добавить мой/наш публичный ключ в
`authorized_keys` целевого сервера, (б) доступ по VPN к сети офиса, где
работает парольный вход на `10.10.4.11`, или (в) вы сами прогоните
`scratchpad/survey_server.py` (только чтение) и пришлёте вывод.

## Риски и чем они закрыты

| Риск | Чем нейтрализуется | Чем проверено |
|---|---|---|
| Потеря 7 постоянных редиректов | Конфиг генерируется **из `vercel.json`**, а не пишется руками: `gen-nginx.py` | `test-nginx.py`: все 7 отдают 308 в тот же адрес |
| Другой код редиректа (301 вместо 308) | В конфиге выставлен 308, как у Vercel | сверка с боевым сайтом показала 308, тест подтверждает |
| Адреса без расширения и слеши на конце | `try_files $uri $uri.html $uri/index.html`, слеш срезается 308-м | 390 адресов карты сайта отдают 200 в реальном nginx |
| Пропажа заголовков безопасности | Заголовки вынесены в сниппет и подключены в каждом `location` — в nginx `add_header` в `location` отменяет серверные | тест ловил именно эту ошибку, сейчас все 5 на месте |
| Потеря кеша статики | `immutable` для `_next/static`, 30 дней для картинок и документов | тест проверяет заголовок `Cache-Control` |
| Битые страницы после выкладки | Сверка нового хоста с боевым по title, h1, canonical и размеру | `parity-check.py` перед переключением DNS |
| Долгий откат при проблеме | Проект остаётся на Vercel; TTL снижается заранее | откат = вернуть A-запись, 5 минут |
| Потеря HTTPS | Сертификат выпускается **до** переключения (DNS-01 или Cloudflare Origin) | `curl -I` по staging-имени |
| Сломать соседний сайт prouniforma | Отдельный `server_name`, отдельные логи, `nginx -t` перед перезагрузкой, никаких правок его конфигов | `nginx -t` + проверка prouniforma.uz после reload |
| Пропажа сайта из индекса | Домен и адреса не меняются, меняется только IP — для Google это не переезд | контроль в Search Console после переключения |

## Что нейтрализовать нельзя, только снизить

1. **Общие простои с Битриксом.** Один сервер на два сайта: перегрузка, ошибка в
   его конфиге или работы по миграции prouniforma затронут и нас. Снижается тем,
   что статику отдаёт nginx напрямую (почти не требует ресурсов), Cloudflare
   продолжает кешировать, а откат на Vercel занимает минуты.
2. **Надёжность площадки.** Vercel — распределённая сеть, один сервер в Ташкенте —
   точка отказа: канал, диск, питание. Закрывается только мониторингом и
   готовностью вернуть DNS.

Остальное из списка выше проверяется автоматически и до переключения.

## Порядок работ

**За 7 дней**
- [ ] Подтвердить, какой сервер целевой. Машина под Битриксом по плану
      prouniforma выводится из эксплуатации — переезд на неё означает переезд дважды.
- [ ] Доступ по SSH (сейчас `10.10.4.11` виден только из сети офиса или по VPN).
- [ ] Завести `staging.cleanroom.uz` на новый IP.

**За 1 день**
- [ ] TTL A-записи cleanroom.uz снизить до 300 секунд.
- [ ] Выложить сайт на staging, закрыть `basic-auth` или отдать `X-Robots-Tag: noindex`.
- [ ] Выпустить сертификат.
- [ ] `python scripts/deploy/parity-check.py https://staging.cleanroom.uz` — ноль расхождений.

**Переключение (окно 15 минут)**
- [ ] Собрать и выложить свежий экспорт: `npx next build`, залить `out/` в
      `/var/www/cleanroom.uz/releases/<дата>`, переключить симлинк `current`.
- [ ] `nginx -t` и `systemctl reload nginx`.
- [ ] Проверить, что **prouniforma.uz** открывается и отдаёт свой сертификат.
- [ ] Снять basic-auth и noindex со staging-конфига.
- [ ] В Cloudflare сменить A-запись cleanroom.uz на новый IP (проксирование оставить включённым).
- [ ] Прогнать `parity-check.py https://cleanroom.uz` ещё раз.

**После**
- [ ] Search Console: «Проверка URL» на 3–5 страницах, отправить sitemap повторно.
- [ ] Следить за отчётом «Индексирование» неделю: рост 404 или 5xx — сигнал.
- [ ] Vercel не удалять минимум 2 недели.
- [ ] Через неделю вернуть TTL на прежнее значение.

## Откат

Вернуть A-запись на Vercel. При TTL 300 секунд сайт возвращается за 5–10 минут,
проект на Vercel всё это время остаётся рабочим.
